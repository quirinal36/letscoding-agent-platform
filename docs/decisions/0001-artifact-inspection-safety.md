# Artifact 검사 안전성 결정

상태: 권장안 적용, 운영자 확인 가능

관련 이슈: #6

## 결정

1차 검사기는 ZIP32의 `store`와 `deflate`만 지원하고 ZIP64, multi-disk, 암호화,
그 밖의 압축 방식은 안정적인 오류 코드로 거부한다. central directory의 항목
수를 먼저 읽어 정책 제한을 넘으면 전체 entry 객체를 만들기 전에 중단한다.
각 파일은 메모리에 전체 해제하지 않고 stream으로 SHA-256과 CRC-32를 계산하며,
선언 크기와 실제 해제 크기 모두 정책 제한을 넘는 즉시 중단한다.

파일명은 UTF-8 flag가 있으면 strict UTF-8로, 없으면 ASCII로만 해석한다. UTF-8
flag 없이 0x80 이상 byte를 사용하는 오래된 CP437 ZIP은 자동 추측하지 않고
`ZIP_FILENAME_ENCODING_UNSUPPORTED`로 거부한다. 원래 entry name의 백슬래시는
슬래시로 고치지 않고 정책 검증기에 그대로 전달한다.

출력 폴더에서는 symlink와 일반 파일이 아닌 항목을 거부하고, 열린 파일의
device/inode/size/mtime을 다시 비교해 검사 중 변경을 fail-closed 처리한다.

현재 중앙 정책 계약에는 최대 경로 길이 값이 없다. 따라서 정책 검증기의 기존
경로 길이 규칙에는 값을 임의로 하드코딩하지 않고, ZIP parser 자체에만 4 KiB
entry-name metadata 안전 상한을 적용한다. 이 상한은 제출 정책이 아니라 parser
자원 보호 한도다.

## 대안과 영향

- ZIP64/CP437을 즉시 지원하면 호환성은 늘지만 parser 표면과 테스트 조합이 크게
  늘어난다. 30 MiB/500개인 1차 제출 정책에서는 ZIP64의 실익이 작다.
- 범용 ZIP 라이브러리를 추가할 수 있으나 원래 파일명 보존, 항목 수 선검사,
  실제 inflate 제한의 동작을 라이브러리 버전에 의존하게 된다. 1차 구현은 필요한
  ZIP32 부분만 명시적으로 읽는다.
- symlink를 따라가면 일부 build 결과를 허용할 수 있으나 출력 루트 밖 파일과
  비밀값이 ZIP에 섞일 위험이 있다.

## 사람 확인이 필요한 시점

실제 사용자 ZIP에서 CP437 또는 ZIP64 거부율이 의미 있게 관측되면 운영자가 지원
확대를 승인해야 한다. 그때 새 구현과 fixture를 추가한 뒤 이 문서 상태를
“대체됨”으로 바꾼다. 중앙 정책에 제출 경로 길이를 새로 넣으려면 정책 Schema와
불변 정책 버전을 함께 발행해야 한다.

## 되돌리기

이 결정은 #6 PR의 검증기 변경만 revert하면 원복된다. 호환성 확대는 기존 거부
코드를 삭제하지 않고 해당 형식을 안전하게 처리한 뒤 성공 경로로 전환한다.
